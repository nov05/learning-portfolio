### **1. The Fundamental Problem**
The core problem of Chapter 10 is **achieving fault-tolerant agreement** in an environment where everything is unreliable. It seeks to provide the **illusion of a single, indestructible machine** (strong consistency) using a cluster of nodes that can crash, pause, or be partitioned by a flaky network.

### **2. Distributed vs. Single-Node Consistency**
Consistency on a single node is a matter of **local hardware enforcement**, such as atomic CPU instructions or memory barriers. In a distributed system, there is **no shared memory and no global "now"**. Truth cannot be established by a single node’s observation; it must be a **consensus property of a majority**.

### **3. The Meaning of "Agreeing"**
For nodes to truly "agree" (Consensus), the system must satisfy four formal properties:
*   **Uniform Agreement:** No two nodes decide differently.
*   **Integrity:** No node decides twice (once a decision is made, it is final).
*   **Validity:** If a node decides value *v*, then *v* must have been proposed by someone.
*   **Termination:** Every node that hasn't crashed eventually reaches a decision (this represents fault tolerance).

### **4. Consistency Models**
The chapter focuses on the spectrum between "eventual" and "strong" behavior:
*   **Eventual Consistency:** Replicas will eventually converge, but the application must handle temporary "time-travel" anomalies and conflicts.
    *   *Application:* Local-first apps, caches where staleness is okay.
*   **Linearizability (Strong Consistency):** The system behaves as if there is only **one copy of the data** and all operations are atomic.
    *   *Guarantee:* **Recency.** As soon as a write is confirmed, all subsequent reads must see it.
    *   *Allows:* High latency and unavailability during network partitions.
    *   *NOT Guarantee:* Isolation for multi-object transactions (that is serializability).
    *   *Application:* Leader election, distributed locking, and uniqueness constraints.
*   **Causal Consistency:** Events appear in an order that makes **causal sense** (e.g., you see a question before its reply).
    *   *Guarantee:* Preserves the "happens-before" relationship.
    *   *Application:* Collaborative editing, social media feeds.

### **5. Key Distinctions**
*   **Linearizability vs. Serializability:** Linearizability is a **recency guarantee** on a single object. Serializability is an **isolation guarantee** for transactions involving multiple objects.
*   **Causality vs. Total Ordering:** Total ordering means every event can be compared to every other event. Causality is a **partial order** where only dependent events have a defined sequence.
*   **Eventual Consistency:** A "best-effort" model that makes no promises about when replicas will match.

### **6. The Problem Consensus Solves**
Consensus solves the problem of **Leadership and Authority**. Without consensus, each node might make its own decision (e.g., "I am the leader"), leading to **Split-Brain**, where two nodes act as the source of truth, resulting in data corruption.

### **7. Core Idea: Paxos and Raft**
These algorithms are essentially **"single-leader replication done right"**. They ensure safety by requiring a **quorum (majority)** of nodes to acknowledge every write and every leader election. This ensures that any successful operation is recorded on enough nodes to survive the failure of a minority.

### **8. The Mechanics of Consensus**
*   **Leader Election:** Uses **Epoch Numbers** (or Terms) to ensure that within any "generation," there is only one unique leader.
*   **Quorums:** Votes from a majority ensure that the quorums for leader election and log appends **overlap**, so a new leader can always find the most recent committed state.
*   **Logs:** A sequence of decided values that provides a **Total Ordering** of operations.
*   **Replicated State Machines:** Every node executes the deterministic operations from the log in the same order, resulting in **identical state** across the cluster. 

### **9. Handling Faults**
In an asynchronous network, a consensus system **cannot distinguish between a crashed node and a slow network**.
*   **Safe Action:** It can **refuse to decide** (sacrifice Liveness/Availability) if a majority cannot be reached.
*   **Forbidden Action:** It **must refuse to make contradictory decisions** (sacrifice Safety), even if the network is partitioned.

### **10. Fundamental Trade-offs**
*   **CAP Theorem:** During a network partition, you must choose between **Linearizability (CP)** and **Availability (AP)**.
*   **Latency:** Linearizability is inherently slow because its response time is proportional to the **uncertainty of network delays**.

### **11. Connections to Ch 8 and Ch 9**
*   **From Ch 8 (Transactions):** **Two-Phase Commit (2PC)** is a form of agreement, but it is not fault-tolerant because it has a single point of failure (the coordinator). Consensus makes 2PC fault-tolerant.
*   **From Ch 9 (Faults):** Ch 9 proves that **local knowledge is a lie** (clocks drift, nodes pause). Ch 10 uses quorums to build a **global truth** out of those unreliable local pieces.

### **The Mental Model: The Distributed "Source of Truth"**

1.  **Distributed State:** You have data replicated across nodes for durability.
2.  **Consistency Models:** You decide how "real" the illusion of a single node needs to be for the user (e.g., **Linearizability** for a lock).
3.  **Ordering and Causality:** To maintain that illusion, you must order events so **cause precedes effect**.
4.  **Consensus:** You use a protocol (Paxos/Raft) to agree on a **Total Order** of events despite node crashes.
5.  **Leader Election:** The protocol picks a "dictator" for an **Epoch** to simplify ordering.
6.  **Replicated Logs:** That dictator appends operations to a log, which is replicated to a **Quorum** for safety.
7.  **Fault Tolerance:** If the dictator dies, the **overlapping majority** ensures the next dictator knows exactly where the last one left off.
8.  **Design Decisions:** You choose to pay the **latency/availability tax** of consensus only for critical coordination (locks, metadata), while using weaker consistency for high-throughput application data.

---

### **5 Rules of Thumb for Distributed Systems**

1.  **A single node cannot trust itself:** It may be paused or partitioned; authority is only valid if verified by a **quorum**.
2.  **A timeout is not a crash:** It provides **zero information** about why a response is missing (network vs. node failure).
3.  **Linearizability is a Recency guarantee, not Isolation:** It ensures you read the latest value, but it won't prevent **Write Skew** in multi-row operations.
4.  **Consensus is "Single-Leader Replication done right":** It automates the "human" step of failover while preventing **Split-Brain**.
5.  **Integrity > Timeliness:** In a system of record, an "apology" for a slow response (Liveness) is better than permanent **Data Corruption** (Safety).
